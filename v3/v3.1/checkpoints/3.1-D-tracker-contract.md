# Checkpoint 3.1-D: tracker contract and local-track records

Date: 15 October 2026

## Scope

This checkpoint defines the boundary for a future single-sensor tracker:

```text
Frame + SensorObservation records -> Tracker -> LocalTrack snapshots
```

It does not select or implement ByteTrack, BoT-SORT, Kalman filtering, optical
flow, appearance matching, or any other association algorithm.

## Contract decisions

- The tracker receives every frame, including frames with no observations, so
  it can later age tracks correctly.
- Every observation in an update must match the frame's sensor ID, frame ID,
  and capture timestamp.
- Observation IDs must be unique within an update.
- Tracker implementations expose a stable `tracker_id` and an explicit
  `reset()` operation for deterministic replay.
- Lifecycle state is one of `tentative`, `confirmed`, or `lost`.
- A `LocalTrack` belongs to exactly one sensor.
- A track snapshot contains its latest observation, first/last seen timestamps,
  observation count, and missed-update count.
- Full observation history is deliberately excluded; that belongs in a later
  event-log module.
- The contract does not prescribe confirmation or retirement thresholds.

## Acceptance checks

- a fake backend can implement the tracker interface without YOLO;
- empty-frame updates are accepted;
- reset is explicit and testable;
- mixed sensor, frame, or timestamp inputs are rejected;
- duplicate observation IDs are rejected;
- lifecycle values serialize as plain strings;
- time ordering, sensor ownership, and counters are validated;
- previous v3.1 and frozen v3 tests remain green.

## Result

**Pass.** All 31 v3.1 tests pass, including tracker-boundary tests, and all 10
frozen v3 regression tests remain green. Python compilation also passes. The
only tracker used is a test double; no production association algorithm was
added.
